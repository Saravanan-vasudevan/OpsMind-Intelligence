# OpsMind

Manufacturing operations analytics: plants, lines, shifts, equipment, production and downtime records, KPI dashboards, **CSV/Excel import with validation, SQL reliability analytics, back-tested forecasting, anomaly detection, Excel reporting and a Power BI model**, with multi-tenant isolation and role-based access.

This is a portfolio project. All demo data is **synthetic** and generated by seeded scripts; no real company data is used.

**Current version: V2 — Data Intelligence** (tag `v2-data-intelligence`). V1 (`v1-fullstack`) is preserved. The AI assistant (V3) is planned in `docs/BLUEPRINT.md` and is **not** implemented.

```
CSV / Excel ─► React upload ─► ASP.NET API ─► Python ETL (validate, dedupe, idempotent) ─► PostgreSQL
                                   ▲                                                         │
React dashboards, forecast, anomalies, reliability, Excel export ◄── ASP.NET ◄── Python (forecast/anomaly/report) ◄┘
                                                                                  Power BI ◄── schema `bi`
```

## What V2 adds

| Area | Implemented |
|---|---|
| ETL | CSV (delimiter sniffing, UTF-8/Windows-1252) and XLSX; header/row validation mirroring the API rules; duplicate and overlap detection; missing values handled without imputation; row-level error reports; atomic load per file; idempotent (same file twice is a no-op); `skip`/`update` conflict policies; strict mode; import history with lineage on every loaded row — `docs/ETL.md` |
| SQL | CTE-based `v_equipment_daily` with a calendar window average, `fn_equipment_reliability` (MTBF, MTTR, availability, Pareto with window functions), `bi` star schema — `docs/SQL_ANALYTICS.md` |
| Dashboards | Existing KPI dashboard + a Reliability page; filters (dates, plant) drive database-computed numbers |
| Forecasting | Four models, rolling-origin backtest on the user's own data, selection by error, empirical interval, refuses when history is too short — `docs/FORECASTING.md` |
| Anomalies | Weekday-aware robust z-score and isolation forest, plain-language explanations, a labelled **synthetic** benchmark with its limits shown in the UI — `docs/ANOMALY_DETECTION.md` |
| Excel | Operations report with live KPI formulas (verified by recalculation), reliability, downtime reasons, anomalies |
| Power BI | Power Query, DAX measures, model notes — `powerbi/` (not opened in Power BI Desktop) |
| Tests | Python 142, SQL 26, frontend 51 — all run; C# 51 methods written, **not run** — `docs/TESTING.md` |

V1 features (auth, structure, data entry, KPIs, CSV export, audit log, tenancy) are unchanged; see `docs/V1_TO_V2.md`.

## How good is the anomaly detection? (short, honest answer)

On a synthetic benchmark with planted problems the default detector found 71–95 % of them across six seeds, but **only 31–62 % of its flags were real** (about 17–30 false flags per 1,000 machine-days). It is a "worth a look" list. The benchmark influenced the design, the data is synthetic, and real-world performance is unknown — table and caveats in `docs/ANOMALY_DETECTION.md`.

## Run it

Requirements: Docker Desktop, or .NET 10 SDK + Node 22 + Python 3.13 + PostgreSQL 16.

```bash
cp .env.example .env        # set POSTGRES_PASSWORD, JWT_SECRET and INTERNAL_API_KEY
docker compose up --build
```

- App: http://localhost:3000 · API Swagger: http://localhost:8080/swagger · intelligence service: internal only
- With `SEED_DEMO_DATA=true` an empty database is filled with 60 days of synthetic data. Demo login: `demo.admin@opsmind.example` (admin) or `demo.user@opsmind.example`, password `Demo-Passw0rd!` (demo only).
- A 14-day forecast needs ≥ 56 days of history and anomaly flags need about 6 weeks: generate and import 120 more days — see `docs/DATA_GENERATION.md`:

```bash
cd services/intelligence && python tools/make_history_csv.py --out ../../data/demo
# then Data imports → upload history_production.csv, then history_downtime.csv
```

Without Docker:

```bash
# Python service
cd services/intelligence && pip install -r requirements.txt
DATABASE_URL=postgresql://user:pass@localhost:5432/opsmind INTERNAL_API_KEY=<same as API> python -m opsmind_intel   # :8000
# backend (Intelligence__BaseUrl=http://localhost:8000, Intelligence__InternalKey=<same>)
cd backend && dotnet build OpsMind.slnx && dotnet test OpsMind.slnx
cd src/OpsMind.Api && dotnet run
# frontend (dev proxy sends /api to http://localhost:8080)
cd frontend && npm ci && npm run dev
```
